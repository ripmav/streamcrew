# Code-ADR-0018: JSON mit `encoding/json/v2`

| | |
|---|---|
| **Status** | Akzeptiert |
| **Datum** | 2026-09-30 |
| **Entscheidung durch** | Projektinhaber (ripmav) |
| **Bezug** | Ergänzt [Code-ADR-0010](0010-polymorphe-serialisierung.md) (Punkt 7); Plan §6.9, §8; [Code-ADR-0006](0006-teststrategie.md), [Code-ADR-0009](0009-ids-und-zeit.md), [Code-ADR-0012](0012-template-engine.md), [Code-ADR-0017](0017-klare-signale-statt-magischer-werte.md) |

## Kontext

- Code-ADR-0010 legt in Punkt 7 fest: `encoding/json` (v1), bis `encoding/json/v2` ohne `GOEXPERIMENT` verfügbar ist; der Wechsel bekommt ein ergänzendes Code-ADR, das die abweichenden Standards von v2 bewertet. Das ist dieses ADR.
- Die Bedingung ist erfüllt (geprüft 2026-09-30): In go1.27.1 gehört das Experiment `jsonv2` zum Standardsatz (`internal/buildcfg`). `encoding/json/v2` und `encoding/json/jsontext` stehen in `api/go1.27.txt` und bauen ohne `GOEXPERIMENT`; nur `GOEXPERIMENT=nojsonv2` schaltet sie ab. Die Annahme vom 2026-09-29, es gehe nur mit dem Experiment, war falsch (Review von PR #42).
- Die Template-Engine nutzt schon `encoding/json/jsontext` für die Kodierung JSON (Code-ADR-0012). Der Rest des Cores nutzt v1: `internal/polydoc`, `internal/domain/command`, `internal/domain/role`, `internal/settings`, `internal/store`, `internal/backup`, `internal/cli` und `internal/vault`.
- v2 unterscheidet sich von v1 laut Paketdokumentation in diesen Punkten:

  | Thema | v1 | v2 |
  |---|---|---|
  | ungültiges UTF-8 beim Lesen | durch U+FFFD ersetzt | abgelehnt (`jsontext.AllowInvalidUTF8`) |
  | doppelte Namen in einem Objekt | erlaubt, der letzte gewinnt | abgelehnt (`jsontext.AllowDuplicateNames`) |
  | Namen von Feldern beim Lesen | ohne Beachtung der Groß- und Kleinschreibung | mit Beachtung (`MatchCaseInsensitiveNames`) |
  | unbekannte Felder | ignoriert (`DisallowUnknownFields`) | ignoriert (`RejectUnknownMembers`) |
  | Reihenfolge der Map-Schlüssel beim Schreiben | sortiert | nicht festgelegt (`Deterministic`) |
  | Nil-Slice, Nil-Map | `null` | `[]`, `{}` (`FormatNilSliceAsNull`, `FormatNilMapAsNull`) |
  | `<`, `>`, `&` in Texten | maskiert | unverändert (`jsontext.EscapeForHTML`) |
  | `time.Duration` | Zahl in Nanosekunden | Fehler ohne Formatangabe |
  | `omitempty` | Nullwert des Go-Typs, auch `false` und `0` | Wert, der als `null`, `""`, `{}` oder `[]` kodiert würde |
  | Zahl in einem `any` | `float64` oder mit `UseNumber` `json.Number` | `float64`, ein Ersatz für `UseNumber` fehlt |

## Entscheidung

1. **Bibliothek:** Der Core nutzt für JSON `encoding/json/v2` und `encoding/json/jsontext`. `encoding/json` (v1) wird nicht mehr importiert. Alle bestehenden Stellen wechseln in einem Schritt, damit kein Paket beide mischt. Eine Ausnahme ist nur eine fremde Schnittstelle, die v1-Typen verlangt; sie steht mit Begründung am Code.
2. **Lesen streng, wie v2 es vorgibt:** Ungültiges UTF-8, doppelte Namen und Namen in anderer Schreibweise werden abgelehnt. Das passt zu Code-ADR-0017 (Ungültiges ablehnen). Bestehende Daten bleiben lesbar: v1 hat beim Schreiben ungültiges UTF-8 ersetzt, doppelte Namen können aus Go-Structs und Maps nicht entstehen, und die Namen stehen so in den Daten, wie die Tags sie vorgeben.
3. **Unbekannte Felder werden je Format ausdrücklich entschieden:** Dokumente nach Code-ADR-0010 lehnen sie ab (`RejectUnknownMembers`), wie bisher mit `DisallowUnknownFields`. Formate, die ältere Versionen lesen müssen, ignorieren sie ausdrücklich und sagen das im Code, etwa das Backup-Manifest und die Schlüsseldatei.
4. **Schreiben reproduzierbar:** Jedes Schreiben nutzt `Deterministic(true)`, damit gespeicherte Bytes, Golden Files und Backups stabil sind. Leere Listen und Maps werden `[]` und `{}`, wie v2 es vorgibt; das entspricht Code-ADR-0017 (Listen nie `null`). `<`, `>` und `&` bleiben unmaskiert. Wer JSON in HTML einbettet, setzt dort `jsontext.EscapeForHTML(true)`.
5. **Dauern und Tags:** Dauern stehen in JSON als Go-Dauer über `polydoc.Duration` (Code-ADR-0009); ein rohes `time.Duration` bleibt ein Fehler. `omitzero` gilt für Nullwerte des Go-Typs, `omitempty` nur für Texte, Listen und Maps. Beim Wechsel wird jedes Tag geprüft, etwa `buildinfo.Info.Modified` (`bool` mit `omitempty`).
6. **`internal/polydoc`:**
   - Kopf lesen mit `jsontext.Decoder`: `type` und `schemaVersion` werden ausdrücklich gelesen, ein fehlendes `schemaVersion` ist ein eigener Fall statt der 0 (Code-ADR-0017).
   - Migrationen arbeiten auf `map[string]jsontext.Value` statt `map[string]any`, damit Zahlen genau bleiben; v2 kennt kein `UseNumber`. Die Signatur von `polydoc.Migration` ändert sich; es gibt noch keine Migration.
   - Rohes JSON hat den Typ `jsontext.Value` statt `json.RawMessage`: `polydoc.Raw`, `polydoc.Unknown`, `command.Record`.
7. **Ausgabe für Menschen:** Die CLI und das Backup-Manifest rücken mit `jsontext.Multiline(true)` und `jsontext.WithIndent("  ")` ein.
8. **Build:** Der Core setzt voraus, dass das Experiment `jsonv2` aktiv ist, wie es in go1.27.1 Standard ist. Ein Build mit `GOEXPERIMENT=nojsonv2` wird nicht unterstützt; die CI baut mit den Standardwerten.
9. **Tests:** Ein Test liest die Golden Files, die v1 geschrieben hat, mit v2 und vergleicht das Ergebnis. Golden Files, deren Bytes sich ändern, werden mit `STREAMCREW_UPDATE_GOLDEN=1` neu geschrieben und im Review geprüft (Code-ADR-0006). Der Fuzz-Test von `internal/polydoc` bleibt.

## Betrachtete Alternativen

| Alternative | Warum nicht |
|---|---|
| bei v1 bleiben | Die Bedingung aus Code-ADR-0010 ist erfüllt. v1 liest nachsichtig (ersetztes UTF-8, doppelte Namen, beliebige Schreibweise), was Code-ADR-0017 widerspricht, und die Template-Engine nutzt schon `jsontext`, sodass zwei Bibliotheken nebeneinander blieben. |
| v2 mit den v1-Standards (`encoding/json.DefaultOptionsV1`) | behält die nachsichtigen Regeln; der Wechsel brächte nur Aufwand |
| nur `internal/polydoc` wechseln | Pakete wie `internal/store` und `internal/domain/command` reichen rohes JSON weiter; ein Mischzustand bräuchte Umwandlungen an jeder Grenze |
| Bibliotheken wie `goccy/go-json` oder `sonic` | zusätzliche Abhängigkeit ohne Nutzen gegenüber der Standardbibliothek |
| warten, bis das Experiment-Tag entfällt | Die API steht bereits in `api/go1.27.txt`; bis dahin entstünde weiterer v1-Code, der später umgestellt werden müsste |

## Konsequenzen

**Positiv:**

- Eingaben werden streng gelesen; mehrdeutiges JSON aus der API, aus Importen oder aus handgeschriebenen Dateien fällt auf, statt still anders verstanden zu werden.
- Gespeicherte Dokumente und Golden Files haben stabile Bytes.
- Migrationen verlieren keine Genauigkeit bei großen Zahlen.
- Der Core nutzt eine JSON-Bibliothek statt zweier.

**Negativ und Risiken:**

- Ein Wechsel über acht Pakete auf einmal, mit geänderten Typen (`jsontext.Value`) in Schnittstellen von `internal/polydoc` und `internal/domain/command`.
- `jsonv2` ist in go1.27.1 formal noch ein Experiment; ändert eine spätere Go-Version die API, zeigt das der Renovate-PR für die neue Go-Version, und der Code wird angepasst.
- Die andere Bedeutung von `omitempty` ist eine Falle: ein `bool` oder eine Zahl mit `omitempty` wird unter v2 nicht mehr weggelassen. Die Prüfung aller Tags beim Wechsel und das Review fangen das ab.
